# 성능과 아직 안 한 것

*[← README](../README.ko.md)  ·  [English](performance.md)*

## 대가

측정: MacBook Air M2 (GPU 8코어), 내장 패널, 백킹 2940x1912, 60Hz 패널.
`--redraw always --no-vsync --fps 1000` 으로 12초, 사이에 8초 쿨다운.

| | fps | 프레임당 |
|---|---|---|
| 통과(셰이더 없음) | 143.4 | 7.0ms |
| `crt.frag` | 82.6 | 12.1ms |
| `crt.frag` (손잡이 승격) | 83.4 | 12.0ms |
| `crt.frag --scale 0.7` | 122.6 | 8.2ms |
| `crt-motion.frag` (지금은 `crt.frag` 에 합쳐졌다) | 71.5 | 14.0ms |
| 합친 `crt.frag`, 흐르는 손잡이 0 | **안 쟀다** | 위 12.1ms 로 돌아와야 맞는다 |
| `water-*.frag` · 사이버펑크 셋 · 인쇄 셋 | **안 쟀다** | |

**전부 60fps(16.7ms) 안에 들어온다.** vsync 를 켜면 다섯 구성이 모두 58~59fps 로
붙으므로, 이 기기에서 `--scale` 을 내릴 이유는 없다. 더 큰 화면이나 더 무거운
셰이더에서 모자랄 때 쓰는 손잡이다.

**손잡이 승격은 공짜다** (82.6 → 83.4, 오차 범위 안). 이 셰이더는 픽셀당 20여 번의
텍스처 페치에 막혀 있어서, 상수가 유니폼이 되며 잃는 폴딩이 드러나지 않는다.
기본으로 켜 둔 근거가 이 값이다.

통과 셰이더에도 7ms 가 드는 것에 주의. 그건 셰이더가 아니라 캡처와 프레젠트의
바닥값이라, 셰이더를 아무리 줄여도 그 아래로는 안 내려간다.

`--scale` 이 화면을 흐리게 하는 이유는 백킹 해상도 때문이다. "더 넓게" 같은
스케일 모드에서 macOS 는 데스크톱을 2940x1912 에 그린 뒤 패널 2560x1664 로
줄인다. 우리 레이어도 그 2940 버퍼에 합성되므로 기본값은 2940 이다. 패널 크기로
그리면 늘렸다 줄이는 셈이 되어 오히려 더 흐리다.

### 그 밖에

- **지연** — 찍어서 그리는 구조라 화면이 한 프레임 남짓 늦다. 오버레이가 화면을
  완전히 덮으므로 겹쳐 보이지는 않고, 전체가 고르게 늦는다. 창을 끌 때 제일
  잘 보인다.
- **커서** — 안 찍는다(`showsCursor = false`). 윈도서버가 오버레이 **위에**
  그리는 진짜 커서가 그대로 남는다. 커서만 셰이더를 안 먹는 대신, 커서에는
  지연이 0 이다. 커서를 유리 안에 넣으면 지연이 눈에 보이는 유일한 자리가 된다.
- **화면 기록 권한** — 첫 실행에 물어본다. 시스템 설정 → 개인정보 보호 및 보안
  → 화면 기록. `build.sh` 가 `.app` 으로 묶고 서명을 하는 게 이것 때문이다.
  알맹이 바이너리만 돌리면 권한이 터미널에 붙는다. **다시 빌드하면 조용히
  끊기는 함정이 있다** — [화면 기록 권한](permissions.ko.md) 참고.
- **보호된 영상(DRM)** — SCK 는 보호 창을 캡처에서 뺀다. 그 자리가 검게 나올
  것으로 보이나 **확인 안 했다.**
- **스크린샷** — 기본값에서는 셰이더가 안 담긴다([되먹임](architecture.ko.md) 참고).
- **배터리와 발열** — 계속 그리기는 정지 화면에서도 주사율대로 GPU 를 쓴다.
  하이프랜드의 `debug:vfr` 과 정확히 같은 갈림길이고, 여기서는 `--redraw auto`(기본)가
  알아서 가른다. [손잡이](knobs.ko.md) 참고. 비용이 픽셀 수 × 프레임 수에 비례하므로
  화면이 크거나 빠를수록 셰이더를 걸기 전부터 더 치르고, 노트북에서는 배터리만큼이나
  열로 나온다. **전력과 온도는 안 쟀다.** 잰 것은 프레임당 비용뿐이다.
- **주사율** — `NSScreen.maximumFramesPerSecond` 로 읽는다. `CGDisplayMode.refreshRate`
  는 내장 ProMotion 패널에서 0 을 돌려주는 것으로 알려져 있고, 그러면 120Hz 를
  60 으로 깎게 된다. 다만 이 갈림은 60Hz 기기에서 드러나지 않아 **ProMotion 에서
  확인 못 했다.**

## 아직 안 한 것

- 체인의 중간 타겟은 `bgra8Unorm` 이다. 단일 패스일 때와 값의 뜻이 같아지는 쪽을
  골랐지만(8비트에서 잘리는 것까지 같다), 대비를 올리는 셰이더를 서너 장 겹치면
  띠가 보일 수 있다. **겹쳐서 재 보지 않았다.**
- 체인의 성능도 안 쟀다. 아래 표는 전부 한 장짜리다.
- **대가 표는 지금 개발하는 기계의 것이 아니다.** MacBook Air M2 의 내장 60Hz
  패널에서 쟀고, 지금 기계는 M4 Pro 에 더 큰 외장 화면 하나를 클램쉘로 물린 것이다.
  거기서는 아무것도 다시 안 쟀고, 두 차이는 서로 반대 방향으로 민다 — GPU 가 빨라지면
  프레임이 싸지고 픽셀이 늘면 비싸진다. 위의 숫자는 전부 옆에 적힌 기계의 것으로만
  읽어야 한다.
- 여러 화면은 코드상 지원하지만 **한 화면에서만 확인했다.** 외장 하나를 클램쉘로
  쓰는 것도 화면 하나라 이 점은 그대로다.
- 배포 타겟이 macOS 13.0 이다. 14.0 이었는데 근거가 없었고, 13.0 은 경고
  하나 없이 빌드된다. 12.3 을 막는 것은 딱 한 줄(`cfg.capturesAudio = false`,
  기본값을 명시한 것)뿐이다. **실제로 돌려 본 것은 15 뿐이고** 13·14 는
  빌드가 된다는 것까지만 확인했다.
- 다른 앱의 전체 화면 위에서, 그리고 미션 컨트롤에서 어떻게 보이는지 확인 안 했다.
  `--space-fix` 는 그래서 기본이 `off` 다 — 스페이스 전환 잔상을 이 기기에서
  아직 못 봤고, 안 보이는 문제에 기본으로 대가를 치를 이유가 없다. 보이면
  `freeze` 부터 (마지막 프레임 유지), 그래도 이상하면 `hide` (창을 잠깐 숨김 —
  그동안 셰이더가 안 걸린 화면이 보인다).
- `water-*.frag` 셋의 비용을 안 쟀다. 위 대가 표에 자리만 비워 뒀다. 노이즈가
  ALU 바운드고 텍스처 페치가 `PRESERVE` 포함 10 번이라 `crt.frag` 의 20 여 번보다
  쌀 것으로 보지만, **그건 추정이지 측정이 아니다.**
- 사이버펑크 셋과 인쇄 셋의 비용도 안 쟀다. `neon.frag` 의 20 탭은 `crt.frag` 의
  블룸(16 탭)보다 무거울 것이 거의 확실하고, 인쇄 셋은 페치가 한둘뿐이라 훨씬
  쌀 것으로 본다. 둘 다 추정이다.
- 여섯 장 다 **화면에 걸어 보고 눈으로 맞추지 않았다.** `--check` 로 번역과
  손잡이 승격만 확인했다. 값들은 그 자리에서 뜻이 통하도록 고른 것이라,
  실제 화면에서는 손잡이를 돌려 볼 자리가 남아 있다.
- 합친 `crt.frag` 에서 **흐르는 손잡이를 0 으로 뒀을 때 옛 `crt.frag` 과 같은
  화면이 나오는지 눈으로 대 보지 않았다.** 코드상으로는 같은 자리에 같은 식이
  남아 있고 `modulate(col, 0, …)` 이 항등이지만, 그건 읽어서 아는 것이지 본
  것이 아니다.
- **유니폼 분기가 실제로 값을 아끼는지 안 쟀다.** 워프가 통째로 같은 쪽으로
  간다는 것에 기대고 있는데, 위 대가 표의 "흐르는 손잡이 0" 줄이 12.1ms 로
  돌아오는지가 그 확인이다.
- 지연을 초로 재지 않았다.
- 나릭스가 관리하는 에이전트를 감지하는 길은 짰지만, **실제로 나릭스로 깔아 놓고
  확인하지는 않았다.** 지금 확인한 것은 앱이 스스로 켜고 끄는 쪽뿐이다.
