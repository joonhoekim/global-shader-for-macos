# Language support

Every string this app shows a person was Korean. Counted, 190 lines.

```
Menu.swift        87      the menu bar. The largest, and the first thing seen
main.swift        69      the usage block + logs and status
Knobs.swift       12      knob errors
LoginItem.swift   10      login item state
Config.swift       8      settings write failures
Renderer.swift     5      pipeline errors
ShaderSource       4      tool not found · promotion folded
Overlay/Capture    7
Instance/Diag      2
```

## What gets moved and what does not

This is the most important part of the document. **Moving all of it is wrong.**

| | Moved | Why |
|---|---|---|
| Menu items · dialogs | **yes** | only people read them |
| `usage` · logs · status | **yes** | only people read them |
| Error text | **yes** | only people read them |
| **Control socket replies** | **no** | it is a protocol |
| JSON keys in `--get` / `--status` | **no** | it is a protocol |
| Knob `doc` (shader comments) | **no** | the shader files are not edited |
| Shader names · file names · folder names | **no** | they belong to the file system |

### Why the control socket is not moved

`Control` replies currently mix in things like:

```swift
return "err usage: set NAME VALUE"
return "err ambiguous name — prefix it with the pass number: \(list)"
return "err no such file: \(p)"
```

Changing these by language **breaks whatever is talking through the socket, depending on
a language setting.** A script that only checks whether it starts with `err` survives;
anything branching on the reason does not. The socket is read by programs, not people, so
stability comes before a friendlier string.

So **every control socket reply is pinned to English.** What is Korean today becomes
English — that is not translation, it is settling the protocol.

The awkward part is where the same string also reaches the CLI (`global-shader --set FOO
1` prints the socket's reply straight to stdout), and **there it simply comes out in
English.** Translating it for display would mean the client parsing the server's reply
and reassembling it, which rebuilds exactly what was just removed.

### Why knob `doc` is not moved

`--get` returns the comment above the `#define` as `doc` along with the value.

**"the shader files are not edited by a single character" is not the reason.** That is a
statement about the program — the app does not rewrite a `.frag` at run time, which is
where it parts ways with Hyprland, where changing a value meant rewriting the file. It
never stopped an author from editing the comments, and they do.

The real reason is worth. This repo's shader headers argue at length about why each value
is what it is, so keeping two versions side by side means editing twice for every value
moved. What that buys is one slider tooltip. And a shader value is not chosen by reading
a number; it is stopped at by looking at the screen.

If it ever becomes worth it, a paragraph per shader goes in `shaders/README.md` — outside
the file, so there is nothing to fall out of step.

## Design

### No `.lproj`

The canonical macOS answer is `Localizable.strings` + `NSLocalizedString`. This does not
use it, for two reasons, both matching judgements this repo has already made twice.

**1. A missing key silently prints the key.** With no translation,
`NSLocalizedString("menu.chain")` puts `menu.chain` on screen. It does not die, it does
not warn, and only someone running in that language sees it. The README gave exactly this
as the reason for not writing a GLSL substituter by hand — *"it goes quietly wrong on some
expression. A tool whose mistakes you have to notice by looking at the screen is
worthless."* A slider that did nothing on a still screen, and a chain that would not apply
being left in the settings, were the same kind of thing.

**2. It has to be the same outside the bundle.** `--check` runs with no window and no
permission, and CI is going to validate shaders with it. Resource loading in the way
creates one more place where "it works from the bundle but comes out differently in CI".
That is precisely why `build.sh` bakes the glslang path into `Generated.swift` — *"no
dependency on the environment at run time."*

### Instead: read JSON, generate Swift

The same place and the same method as `Generated.swift`.

```
i18n/
  en.json          the reference. It decides the key set
  ko.json          the translation
tools/
  gen-strings.swift   JSON → Sources/Strings.swift
```

`build.sh` calls it right next to where it writes `Generated.swift`.

**A key present in `en.json` and absent from `ko.json` makes the generator print every
missing key and exit non-zero.** That stops the build. This is everything gained by
throwing `.lproj` away.

### JSON schema

```json
{
  "menu.chain.moveUp": {
    "en": "Move up"
  },
  "menu.title.bypassed": {
    "args": ["Int"],
    "en": "Off — %1$d pass(es)",
    "note": "Title of the menu bar status item, with the shader switched off."
  },
  "knob.err.noPass": {
    "args": ["Int", "Int"],
    "en": "no pass %1$d in the chain (%2$d now)"
  }
}
```

- No `args` means a string with no arguments
- **Placeholders must be positional — `%1$@` · `%2$d`.** Word order differs by language,
  so `no %@ in %@` cannot be reordered in translation
- `note` is seen only by whoever translates it. The generator passes it through as a comment
- `ko.json` holds the same keys with strings alone: `{"menu.chain.moveUp": "위로"}`

### What is generated

```swift
// Generated by tools/gen-strings.swift. Do not edit by hand.
enum Str {
    /// Title of the menu bar status item, with the shader switched off.
    static func menu_title_bypassed(_ a1: Int) -> String {
        String(format: pick(en: "Off — %1$d pass(es)",
                            ko: "꺼 둠 — %1$d칸"), a1)
    }
    static var menu_chain_moveUp: String { pick(en: "Move up", ko: "위로") }
}
```

Argument count and types are baked into the signature, so **a caller that gets them wrong
does not compile.** That is the second thing `.lproj` cannot give.

### How the language is decided

```
--lang ko                     this run only
GS_LANG=ko                    environment variable (the place launchd would set it)
"lang": "ko" in config.json   where a change from the menu lands
system (Locale.preferredLanguages)
en                            when nothing decides
```

`lang: String? = nil` is added to `Config` in `Config.swift`. `nil` means "follow the
system", and it belongs in `Config` rather than `RuntimeOptions` — a language is taste,
not a run option used for one measurement, so it follows the rule for `shaderPaths`
rather than the one for `--scale` (the comment at the top of `main.swift`).

**Resolution happens once at process start and is frozen globally.** Changing the language
mid-run would mean rebuilding the menu, which happens on every open anyway. Freezing it is
about not diverging from the log already written.

### `Info.plist` and System Settings

`CFBundleLocalizations` lists `en` · `ko`. That makes the app appear in System Settings →
General → Language & Region, and the choice made there is written to the app's
`AppleLanguages` and comes back through `Locale.preferredLanguages`.

> **To verify**: whether `CFBundleLocalizations` alone puts it in that list with no
> `.lproj` folders. If not, whether empty `en.lproj` · `ko.lproj` in the bundle does it.
> If that fails, add `Settings → Language` to the menu.

### Korean particles

`%1$@ 을(를) 못 찾았다` already exists in `ShaderSource.swift`. In the translation table,
this kind of sentence is **rewritten to avoid particles** — `못 찾았다: %1$@`. Writing a
function that picks the particle by final consonant is possible, but it is the kind of
thing that demands another language's rules the moment a third language arrives.

## Languages

Starting with `en` and `ko`. `en` is the reference — the Korean currently in the source
moves down into the translation.

Taking `en` as the reference is structural, not a preference. The reference language
defines the key set, so it is the language you are necessarily made to write first when
adding a string. Once this repo is public, issues and pull requests will arrive in
English, and demanding Korean first at that point blocks contribution.

Adding a third language costs one `i18n/<code>.json` file and one line in `pick()`.

## Order of work

1. **The generator and the plumbing first.** Put two keys in `i18n/en.json`, wire it
   through `build.sh`, and watch the app run on an empty table. Confirm that a missing
   key stops the build.
2. **`Menu.swift`.** 87 strings. The largest and the simplest in shape (nearly all short
   noun phrases with no arguments). Finishing here finishes most of what is visible.
3. **Pin control socket replies to English.** Settling a protocol rather than translating,
   so it is a step of its own. It is all in the `handle(_ line:)` family in `main.swift`.
4. **The rest of `main.swift`.** In `usage`, **one block is one key, not one line per
   line**. Splitting the option descriptions line by line breaks the alignment; kept
   whole, a translator can align the columns to fit their own language.
5. **The remaining 6 files.** 34 strings.
6. **Re-read `en.json`.** Moving Korean into English leaves the original's voice behind.
   The Korean here is short declarative sentences, and carried over as is the English
   reads not terse but odd. Sweep the English alone at the end.

## Afterward

The comments in `shaders/**/*.frag` were Korean too, and those files are among the most
readable documentation in the repo — but to an English-speaking reader they may as well
not exist.

They were **not** touched during this work: the concern here is the string table, and the
two are separable. They were moved to English later, along with the source comments, when
the repo was prepared for publication. What remains Korean is what is read as Korean:
`i18n/ko.json` and the `*.ko.md` documents.
