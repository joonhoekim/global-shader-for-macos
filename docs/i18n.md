# Languages

*[← README](../README.md)  ·  [한국어](i18n.ko.md)*

Menus, logs and `--help` all come out in English or Korean. Four places choose
it, first one wins:

```
--lang ko                     this run only
GS_LANG=ko                    environment variable (the place to put it in launchd)
"lang" in config.json         Settings → Language in the menu
the system (Locale.preferredLanguages)
```

`Info.plist` declares `CFBundleLocalizations`, so the app also shows up under
**System Settings → General → Language & Region → Applications**. There is still
a Language item in the menu, because few people know the way to that list.

## The three things that are not translated

Translating everything would be wrong.

**Control socket replies.** What goes over that hole is always English. It is a
hole for programs, not for people, and if the answer changed with a language
setting, anything that branches on the reason would stop working. `--set` and
`--get` print the socket reply verbatim, so their output is English too.

**The JSON keys in `--get`.** Same reason.

**Knob documentation (`doc`).** That text is a comment inside a `.frag` file.

It *could* be translated. The rule that not a character of a shader file changes
is about the **program** — the app never rewrites a `.frag` at runtime, which is
what makes a knob different here from a knob on Hyprland. It was never a rule
about the author editing a comment.

It is not translated because of what that would cost. The shader headers are
long-form arguments about why each value is what it is; keeping two of them in
step would mean two edits every time a value moves, in exchange for a slider
tooltip. And a shader value is not picked by reading numbers — you watch the
screen and stop.

If it starts to matter, the right shape is a `shaders/README.md` with an
English paragraph per shader: outside the files, so there is nothing to drift.

## Why not `.lproj`

The standard on macOS is `Localizable.strings` with `NSLocalizedString`. This
repo does not use it, **because a missing translation prints the key on screen.**
Nothing crashes, nothing warns, and only the person running in that language ever
sees it.

This repo has already refused that failure twice — the hand-written GLSL
translator (silently wrong values) and the slider on a still screen (silently
dead values). There is no reason to make an exception here.

Instead, `tools/gen-strings.swift` turns `i18n/*.json` into
`Sources/Strings.swift`. `build.sh` calls it right next to where it writes
`Generated.swift`.

```
i18n/
  en.json    the base. it defines the key set
  ko.json    a translation
```

Three things come out of that.

- **A missing translation stops the build.** The generator prints every missing
  key and exits non-zero.
- **Placeholder count and types are baked into the signature.** A caller that
  gets them wrong does not compile. Because word order differs per language, it
  also forces positional `%1$@` forms.
- **Nothing is read from the bundle at runtime.** `--check` runs with no window
  and no permission and CI validates shaders with it; a resource-loading step
  would create one more place where "it works from the bundle but behaves
  differently in CI".

Adding a language costs one `i18n/<code>.json`.
